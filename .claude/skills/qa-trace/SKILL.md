# UI ↔ бекенд

Найцінніші баги живуть у розриві між тим, що показав інтерфейс, і тим, що реально
сталося на сервері. «Кнопка спрацювала, а в логах 500 і мовчазний ретрай» —
руками таке не ловиться.

## Крок 1. Зафіксувати момент

Потрібен точний час дії з точністю до секунди і, якщо є, ідентифікатор запиту.
Бери з `mcp__claude-in-chrome__read_network_requests`: URL, статус, час, заголовки
відповіді (`x-request-id`, `traceparent`, `x-correlation-id` — що є).

Без цього пошук у логах перетворюється на вгадування.

## Крок 2. Kibana

```
http://foxtrot01-dev-dyn-kibana-g.foxtrot.cloud/app/discover
Data view: aee7f12d-a673-4b83-8a93-f32ff9600304
```

**Потрібен VPN.** Якщо сторінка не відкривається — перш ніж робити висновки,
спитай Ярослава, чи увімкнений VPN. Це не помилка логів і не падіння стенду.
У пам'яті є два відомі підводні камені його VPN (MTU на домашньому Wi-Fi і
конфлікт маршруту 192.168.1.0/24) — якщо тунель стоїть, а дані не йдуть, згадай про них.

Шукай у вікні ±30 секунд навколо дії. Спершу за request id, якщо він є; якщо ні —
за ендпоінтом і рівнем `error`/`warn`.

Дві пастки, на які легко наступити:

- **Час у Discover на годину раніший за той, що в логу.** Discover малює в
  `Europe/Warsaw`, а сам запис іде з `+03:00`. Тому доказ шукай і фіксуй за `_id`,
  а не за часом — час у звіті наводь, але не покладайся на нього при пошуку.
- **Помилка — це `level: Error`.** `Warning` тут інформаційний і сам собою бага не
  означає. Підтягувати `Warning` можна лише як доказ до вже знайденого `Error`.

Далі звужуй: сам стектрейс рідко відповідає на питання «чому». Дивись, що було
**перед** помилкою в тому ж запиті — зазвичай причина там.

### Обов'язково: зафіксувати документ

Знайшов потрібний лог — **одразу розгорни його й запиши `_id` і `_index`**.
Без цього посилання на лог не варте нічого: повернутись до рівно того самого
документа за часом і текстом неможливо, у логах повно однакових рядків з тією
самою мілісекундою.

Записуй у такому вигляді:

```
_id: VnbpIqABMExvpF40phZ8
_index: logstash9-2026.09.12
@timestamp: 2026-09-12 21:38:09.019
```

Разом з цим **збережи сам JSON документа у файл** (вкладка JSON у правій панелі
Discover) в `qa-toolkit/tasks/<KEY>/`. Індекси ротуються — через кілька тижнів
документа може не стати, і від голого `_id` не лишиться користі.

Якщо релевантних документів кілька — зберігай `_id` кожного, а не «десь там о 21:38».

Для важких прогонів по логах бери агента `qa-pr-log-analyst` — він для цього і є,
а ти лишаєш у розмові тільки висновок.

## Крок 3. Звірка з API

Колекції: `PostmanCollection/`, `PostmanTests/`. `newman` встановлений глобально.

```
newman run "PostmanCollection/Фокстрот.postman_collection.json" -e "PostmanCollection/Prod.env.json"
```

Навіщо це в ручному тестуванні:

- **Фронт vs бекенд.** Те саме невалідне значення, яке відхилив UI, відправ прямо
  в API. Якщо бекенд його прийняв — це справжній баг, а не косметика.
- **Що реально повернув сервер.** UI показав «Успішно», а в тілі відповіді
  `{"status":"partial"}` — таке видно тільки в сирій відповіді.
- **Стан після дії.** Після ручної дії смикни GET і подивись, чи дані справді
  збереглись так, як показав інтерфейс.

## Крок 4. Висновок

Формулюй одним абзацом і розділяй три різні речі:

1. Що побачив користувач.
2. Що реально сталося на сервері.
3. Де саме розрив — фронт приховав помилку / бекенд відповів неправильно /
   обидва праві, а баг у даних.

Далі — `qa-bug`, і вкладай у репорт витяг з логів (з `_id` та `_index`), сиру
відповідь API і шляхи до збережених файлів. Баг з бекенд-слідом розробник закриває
вдесятеро швидше, а з `_id` він відкриє той самий лог сам, не перепитуючи тебе.
