# Граничні дані та прогін форм

Набори: `qa-toolkit/testdata/payloads.json` — `email`, `text`, `number`, `phone_ua`,
`date`, `password`, `sanitization`, `url`, `filename`.
Кожне значення має `expect`: `accept` (має пройти), `reject` (має відхилитись зі
зрозумілим повідомленням), `escape` (має зберегтись як текст і вивестись екранованим).

## Просто дати дані

```
node qa-toolkit/testdata/autofill.js --list            які набори є
node qa-toolkit/testdata/autofill.js --list email      значення набору
```

Коли Ярослав питає «які кейси для цього поля» — не вигадуй з голови, бери з набору
і **додай те, що специфічне саме для цього поля**: його бізнес-обмеження, звʼязки
з іншими полями, залежність від ролі.

## Автоматичний прогін

```
node qa-toolkit/testdata/autofill.js <url> --field "<css>" --set <набір> \
     [--submit "<css кнопки>"] [--error "<css помилки>"] [--storage auth.json] [--headed]
```

Скрипт по кожному значенню: перезавантажує сторінку, заповнює поле, знімає
`validationMessage` браузера, шукає видимий текст помилки, фіксує, чи відправилась
форма — і ставить вердикт проти `expect`.

Читай у звіті насамперед два блоки:

- **Розбіжності** — валідне відхилено або невалідне прийнято. Це кандидати в баги.
- **Перевірити очима** — набір `sanitization`. Скрипт бачить лише, чи виконався код
  на самій сторінці. Погана санітизація проявляється **там, де значення виводиться
  назад**: у списку, в картці, в листі, в PDF, в експорті CSV. Іди й перевір ці місця
  сам через браузер, не залишай це на «ну мабуть нормально».

## Важливо про хибні спрацювання

HTML5-валідація `type=email` має відомі особливості, які скрипт чесно покаже як
розбіжності — не неси їх у Jira як баги не розібравшись:

- `test@example` (домен без TLD) — браузер **пропускає**, це за специфікацією;
  баг лише тоді, коли бекенд теж пропускає.
- Кириличні домени (`пошта.укр`) — браузер **ріже**; чи це баг, залежить від того,
  чи обіцяє продукт підтримку IDN.
- Локальна частина > 64 символів — браузер не перевіряє довжину, має ловити бекенд.

Тому після прогону UI перевіряй те саме на API — колекції в `PostmanCollection/`,
запуск через `newman` (див. skill `qa-trace`). Валідація на фронті без валідації
на бекенді — це і є баг, який варто завести.
