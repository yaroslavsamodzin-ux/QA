# QA — щоденний робочий процес

Цей репозиторій — робоче середовище QA-інженера (Ярослав). Claude тут виконує роль
щоденного QA-помічника: рев'ю PR розробників, робота із задачами в Jira, тестування
фічей, перевірка логів на помилки.

## Продукт, який тестуємо

**Foxtrot** — інтернет-магазин www.foxtrot.com.ua. Код у приватному GitLab
`git.foxtrot.ua`, група `new-cms-foxtrot/evinent` (24 репозиторії, потрібен VPN).

- **Стек:** ASP.NET Core MVC (Razor), Redis, Elasticsearch, Kubernetes + Helm, AWS.
- **Ключові репо:** `foxtrot-site` (сайт), `foxtrot-api` (новий API),
  `foxtrot-common` (спільна бібліотека API), `foxtrot-api-main` / `-catalog` /
  `-cms` / `-exchange`.
- **Стенди:** прод — www.foxtrot.com.ua; дев — динамічні, `<user>.foxtrot.cloud`
  (той самий домен, що й Kibana). Збірка іменується `dev_NNNN`.
- **Задачі Jira:** префікси `CMS-` і `FMA-`. MR: `[#CMS-1234] Опис`, гілка
  `CMS-1234_опис`, ціль `master`.
- **Одна задача — часто кілька MR у різних репо** (site + common + api-*). Перед
  рев'ю чи тестуванням перевіряти, чи немає ще MR по тій самій задачі.
- **Мітки MR = процес:** `Reviewed` → `On_Testing` → `QA_Approved` / `Need_Fix` /
  `Code_Review_Failed`. `Db_changed`, `Conf_changed`, `NuGet_changed` означають, що
  стенду потрібні міграція, зміна конфігу чи повний ребілд — без них «не працює» це
  не баг.
- **Прапорці фіч** живуть у `foxtrot.site/appsettings.json` (`CustomSettings`) —
  перевіряти перед заведенням бага «фіча відсутня».

Подробиці — мапа всіх репозиторіїв, межі валідації полів, наявні автотести, як
читати файли GitLab без клієнта — у `docs/product-foxtrot.md`. Оновлювати той файл,
коли з'являються нові репо або змінюється процес.

## Зовнішні системи — тільки читання

**У Jira, Kibana, GitHub/GitLab і будь-якій іншій зовнішній системі — виключно
читання.** Нічого не писати, не створювати, не редагувати, не видаляти: ні задач,
ні коментарів, ні статусів, ні лейблів, ні апрувів, ні вкладень, ні збережених
пошуків і дашбордів. Не надсилати форми й не тиснути кнопки, що змінюють стан на
боці сервісу.

Це правило підстраховане технічно — `PreToolUse` hook
`.claude/hooks/readonly-guard.js` бачить кожен виклик до того, як той виконався:
вкладення, `javascript_tool` і мутуючі `gh`/`glab`/`curl` у бік цих систем блокує,
клік і ввід на їхніх сторінках виносить на підтвердження Ярославу. Режими —
`readonly-guard.config.json`. Hook не замінює правило: він не бачить хоста у
вкладці, яку відкрили руками.

Результат роботи — баг-репорт, коментар до PR, чекліст, звіт про тестування —
**готується текстом і віддається Ярославу**. Публікує його він сам, своїми руками.

**Докази зберігай у файли, не лише в чат.** Скріншоти, GIF, витяги з логів, тіла
запитів і відповідей клади в `qa-toolkit/tasks/<KEY>/` (напр.
`qa-toolkit/tasks/CMS-25413/`) і посилайся на них шляхом. Те, що показане тільки в
переписці, зникне разом із сесією — а у вкладення до задачі піде файл.

**Єдиний виняток — тестовані стенди.** Продукт, який ми тестуємо, чіпати можна:
заповнювати форми, створювати тестові сутності, проходити сценарії — це і є робота.
Але незворотні дії там (видалення, зміна чужих даних, дії від чужого імені)
питаються окремо щоразу.

## Рев'ю PR і задачі в Jira

- Фіксованого GitHub org/repo немає, `gh` не налаштований, API-доступу до Jira
  теж — посилання дають щоразу окремо, відкриваємо через браузер.
- Для рев'ю PR за посиланням і для важких прогонів по логах — агент
  `qa-pr-log-analyst`.
- Якщо до PR є задача в Jira — попроси лінк і звір зміни з acceptance criteria.
- Перед тестуванням задачі — прочитати опис, критерії приймання, пов'язані PR.

## Тестування

Тестовий фреймворк у репо — Playwright (`@playwright/test`), запуск через
`npx playwright test`. Є Postman-колекції та тести в `PostmanCollection/` і
`PostmanTests/`. Python-залежності — `requirements.txt`, віртуальне середовище `.venv`.

**Одна зміна — не одна сторінка.** У задачі буде названа одна сторінка, але той
самий блок живе на кількох, і через редизайн реалізації там різні: фікс під нову
верстку легко ламає стару. Перед прогоном знайти всі сторінки з блоком і пройти
кожну — окремо нові, окремо старі. Перелік сторінок з еталонними URL прода, техніка
побудови матриці (ширини × браузери × варіанти даних), межі можливостей Playwright
і уроки про вимірювання блоків — у skill `qa-responsive`, Кроки 0–2.

**Скріншот на кожну заявлену ширину й сторінку, з десктопу і з мобілки.** Немає
кадру — не пиши це в список перевіреного. Не писати «працює», якщо перевірено
тільки в Chrome останньої версії: у звіті прямо вказувати, де саме перевірено, що
було емуляцією, а що — реальним пристроєм.

## qa-toolkit — інструменти під ручне тестування

Набір у `qa-toolkit/`, докладно — `qa-toolkit/README.md`. Кожен пункт має слеш-команду;
бери її сам, коли задача підходить, не чекай, поки Ярослав назве її явно.

| Команда | Коли брати |
|---|---|
| `/qa-android` | тестування на реальному Android-телефоні через adb |
| `/qa-watch` | стежити за консоллю й мережею, поки Ярослав тестує руками |
| `/qa-bug` | він каже «ось баг» — зібрати готовий репорт під Jira |
| `/qa-checklist` | є задача в Jira — скласти чекліст перед тестуванням |
| `/qa-run` | прогнати чекліст, скласти звіт про тестування зі статусами й ризиками |
| `/qa-responsive` | перевірити верстку на всіх ширинах / візуальна регресія |
| `/qa-browsershot` | знімок вікна Firefox/Edge/Opera, які Ярослав відкрив руками |
| `/qa-testdata` | граничні значення для полів, автопрогін форми |
| `/qa-trace` | звірити побачене в UI з логами Kibana та відповідями API |

Результати прогонів і докази по задачах (`report/`, `tasks/`, `test-results/`) у git
не потрапляють. Еталони візуальної регресії в `qa-toolkit/visual/baseline/` —
навпаки, комітяться.

## Браузер

- До Claude in Chrome підключені два локальні Chrome: **Work Chrome** і
  **Personal Chrome**.
- **Усі робочі задачі — тільки у Work Chrome:** Jira, GitLab, Kibana, тестові стенди.
  Там живуть потрібні сесії й доступи. Personal Chrome для роботи не використовувати.
- `list_connected_browsers` повертає старі імена (`Browser 1` / `Browser 2`) і не дає
  зіставити deviceId з назвою. Тому вибір робити через `switch_browser`: Ярослав
  тисне **Connect** у потрібному вікні, і тулзи відповідають, який саме обрано.
- Ознака, що обрано правильний: у Work Chrome `jira.entri.com.ua/browse/<KEY>`
  відкривається без форми логіна. Якщо просить логін — обрано не той браузер.

## Сповіщення на телефон

Ярослав відходить від комп'ютера, поки йде довга задача. Слати `PushNotification`,
не чекаючи прохання, у двох випадках: **завершив задачу** (робота реально здана, а не
«запустив і чекаю») і **стало через нього** (потрібне рішення, доступ, VPN, логін,
апрув). У тексті одразу суть: `CMS-25413: чекліст пройдено, 2 фейли` замість «готово».

**Один пуш на задачу, в кінці.** Два пуші підряд — другий не побачать: телефон мовчки
підміняє ним перший у шторці, без звуку й банера (перевірено 14.09.2026: різниця ~2 хв
— не помічено, ~12 хв — прийшов). `Mobile push requested` означає «запит передано», не
«доставлено». Коли Ярослав сидить у терміналі, харнес глушить пуш як дублікат і
відповідає `Not sent` — це нормально.

## Compact Instructions

При стисненні контексту обов'язково зберегти:

- ключ задачі й URL стенда, на якому йде робота;
- перелік **уже перевірених** сторінок і ширин разом зі шляхами до знятих кадрів —
  і перелік тих, що лишились;
- знайдені дефекти: короткий опис, сторінка, ширина, шлях до доказу;
- `_id` і `_index` знайдених документів Kibana;
- відкриті питання з `qa-toolkit/tasks/<KEY>/questions/`;
- те, що Ярослав просив зробити інакше в цій сесії.
